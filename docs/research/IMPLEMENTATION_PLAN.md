# IMPLEMENTATION_PLAN — Vishar Color Study (PWA)

Дата: 2026-10-18, обновлено после разбора веб-версии оригинала (TECHNICAL_RESEARCH, разделы 3 и 5.7). Основа: FEATURE_AUDIT.md и TECHNICAL_RESEARCH.md. Архитектура принята владельцем 2026-10-18. Дальше идёт этап 0 (диагностический стенд), основной интерфейс пока не разрабатывается.

Что изменилось после разбора оригинала:
- Оригинал на вебе считает всё в главном потоке и замораживает интерфейс на 1,6–2,1 с при Simplify. Worker в нашей архитектуре — главное отличие, а не оптимизация.
- Оригинал держит рабочую копию 1080 px и экспортирует в 1080 px. Наш экспорт в полном разрешении — реальное преимущество для печати трафарета.
- Values оригинала близко воспроизводится 1-D k-means по luma с весом по числу пикселей: 99,8–100 % на трёх фото и 89,9 % на пейзаже, так что алгоритм восстановлен не полностью. Notan = медиана luma. Медиана подтверждённо ломается на эскизах с большим фоном, поэтому Otsu остаётся в плане.
- Drawing в оригинале — две нейросети по 17 МБ. Для MVP берём классические фильтры (XDoG, Canny), нейросеть — отдельное решение (раздел 8).
- Веб-версия оригинала не работает офлайн. Наш Service Worker закрывает и это.

Уточнения владельца при приёмке архитектуры (2026-10-18):
1. Values на пейзаже совпадает на 89,9 %, алгоритм не называем полностью восстановленным.
2. Обычный k-means по luma с весом по числу пикселей остаётся режимом совместимости с оригиналом. Вес √count — дополнительная опция для малого числа уровней.
3. Замеры Chromium и Node отделены от ожиданий для Safari. Результаты одного устройства на другое не переносим (раздел 2, «Измерено и ожидаемо»).
4. Для 48 МП отдельно расписаны декодирование, тайловый экспорт, границы тайлов и поведение при нехватке памяти (раздел 2, «Фото 48 МП»).
5. Тату-проверки выдают предупреждения о возможной потере читаемости, а не прогноз заживления. Все пороги настраиваются (раздел 5).

## 1. Цель и границы

Vishar Color Study — PWA для анализа референсов и подготовки тату-эскизов. Главная платформа — Safari на iPhone, приложение на домашнем экране. Фото обрабатываются только на устройстве и никуда не отправляются.

Из Color Study берём пользовательские возможности анализа: пипетку с картой цветов, автоизвлечение палитры, Values, Notan, Temperature, Simplify, Drawing, Highlight, сетку, экспорт. Код, графику и тексты оригинала не берём.

Не берём в MVP: смешивание масляных красок с камерой и каталоги пигментов. Для тату они не нужны, а данные спектральных кривых пришлось бы собирать с нуля. Вместо этого будет палитра тату-пигментов (раздел 6).

Не делаем: Cloudflare- и Supabase-проекты, серверную обработку, аккаунты. Если позже понадобится синхронизация, это отдельное решение.

## 2. Архитектура

```
┌──────────── главный поток (UI) ────────────┐
│  экраны, жесты, слайдеры                   │
│  <canvas> вывода: WebGL2-просмотрщик        │   ← только отображение готовых текстур
└───────▲─────────────────────┬──────────────┘
        │ результаты (ImageBitmap, массивы, transfer)
        │                     │ команды (Comlink)
┌───────┴─────────────────────▼──────────────┐
│  Engine Worker                              │
│  • декодирование: createImageBitmap         │
│  • пирамида: preview ~1 МП, analysis ~2 МП  │
│  • GPU-пасс: OffscreenCanvas + WebGL2       │   Lab, blur, пороги, температура,
│    (WebGPU как ускоритель на iOS 26+)       │   присвоение кластеров, Sobel/XDoG
│  • CPU-пасс: гистограммы, k-means по        │   то, что плохо ложится на шейдер
│    выборке, связные компоненты, слияние     │
│  • export-пасс: тайлы полного разрешения    │
└───────▲─────────────────────┬──────────────┘
        │                     │
┌───────┴──────┐      ┌───────▼──────────────┐
│ IndexedDB    │      │ OPFS                 │
│ проекты,     │      │ оригиналы фото,      │
│ палитры,     │      │ кэш превью и         │
│ настройки    │      │ результатов анализа  │
└──────────────┘      └──────────────────────┘
Service Worker (Workbox): precache оболочки и движка → полный офлайн
```

Ключевые правила:
1. **Рабочая копия вместо оригинала.** Интерактив считается на копии ~1–2 МП (длинная сторона 1280–1600; оригинал использует 1080). Замер в Chromium 141 на сервере, не на iPhone: 12 МП → 1600 px в Worker занял 115 мс, а Simplify на полном 12 МП — 5,1 с против 1,4 с на рабочей копии (TECHNICAL_RESEARCH, 5.5). Главный поток никогда не считает пиксели: у оригинала это даёт заморозку до 2,1 с (TECHNICAL_RESEARCH, 5.7.6).
2. **Попиксельное — на GPU.** Lab, сглаживание, пороги Values/Notan, температура, присвоение кластеров, Highlight, Sobel/XDoG идут фрагментными шейдерами WebGL2. Слайдер меняет uniform, а не пересчитывает массивы в JS.
3. **Структурное — на CPU в Worker.** Гистограммы, 1-D k-means, k-means по выборке 40 тыс. пикселей, связные компоненты, слияние мелких областей, графовая сегментация.
4. **Полное разрешение — только при экспорте**, тайлами (старт 2048 px) с перекрытием под радиус всех фильтров, подробности в разделе «Фото 48 МП». Ни одного холста больше 4096×4096 одновременно, пока на устройстве не подтверждено, что лимит 16,7 МП снят.
5. **Память.** Lab хранится в Uint8 (L 0–255, a/b со смещением 128) или в текстуре RGBA8, а не во float32: для 48 МП разница 195 МБ против 585 МБ. Отработанные холсты обнуляются (`width = height = 0`).
6. **Ни одного сетевого запроса с пикселями.** CSP `connect-src 'self'`, проверка в e2e-тесте.

| Contours / Sketch | GPU (Sobel, XDoG); hysteresis Canny и векторизация на CPU | оригинал использует ONNX-модели 2×17 МБ, на iPhone только WASM-бэкенд и вход 512 px. Классические фильтры работают на полном разрешении и без загрузки 34 МБ |
| WASM | только если профилирование на iPhone покажет узкое место в CPU-пассах (слияние регионов, Graph) | JS-версии укладываются в бюджет на рабочей копии |

### Измерено и ожидаемо

- Все времена в этом плане и в TECHNICAL_RESEARCH сняты в Node 22 и Chromium 141 headless на серверном Xeon 2.1 ГГц, WebGL через SwiftShader. Это ИЗМЕРЕНО только для этой среды.
- Для Safari на iPhone своих чисел нет. Критерии этапов в разделе 6 — целевые значения, а не прогноз. Этап 0 их подтверждает или пересматривает.
- Результаты одного устройства на другое не переносим. Замер на одном iPhone не считается результатом для другой модели, поэтому в таблице этапа 0 у каждой строки есть модель, версия iOS и режим (Safari или домашний экран).

### Фото 48 МП: декодирование, тайлы, нехватка памяти

Статус: расчёт и план. На iPhone ничего из этого пока не измерено.

Декодирование:
- Кадр 8064×6048 = 48,8 МП, один буфер RGBA = 195 МБ. Это почти в 3 раза больше исторического лимита canvas 16,7 МП, поэтому полный кадр в один canvas не рисуем.
- Рабочую копию получаем через `createImageBitmap(blob, { resizeWidth, resizeQuality, imageOrientation: 'from-image' })`, чтобы декодер сразу отдал уменьшенный кадр. Поддерживает ли Safari эти опции и декодирует ли он при этом полный кадр, проверяет этап 0.
- Запасной путь: один раз декодировать в ImageBitmap, уменьшить по частям в OffscreenCanvas не больше 4096×4096 и сразу вызвать `bitmap.close()`.
- HEIC декодирует только нативный декодер Safari, без WASM-библиотек. ProRAW и DNG вне MVP.
- В памяти одновременно не больше одного полного декодированного кадра. Блоб исходника храним, пиксели полного кадра освобождаем сразу после рабочей копии.

Тайловый экспорт и границы тайлов:
- Полное разрешение считается тайлами. Стартовый размер 2048×2048 (4,2 МП, 16,8 МБ RGBA); он настраивается и автоматически уменьшается при ошибке.
- Каждый тайл читается из исходника с полем перекрытия: максимальный радиус всех фильтров цепочки (сглаживание, blur, Sobel/XDoG, дилатация) плюс 2 px. После обработки поле обрезается, в результат идёт только центр, поэтому на стыках нет швов от фильтров.
- Глобальные параметры считаются один раз на рабочей копии и одинаково применяются ко всем тайлам: пороги Values и Notan, центры кластеров Simplify, палитра, нормировка температуры. Тайл не считает свою гистограмму, иначе соседние тайлы получат разные уровни.
- Операции, которым нужен весь кадр (связные компоненты, слияние мелких областей, графовая сегментация), напрямую не тайлятся. Метки считаем на рабочей копии, масштабируем вверх и уточняем границы по исходнику внутри тайла. Если качество окажется плохим, экспорт этих видов ограничиваем двойным размером рабочей копии. Решение принимаем на этапе 3.
- Итог пишется построчно потоковым PNG-энкодером в Worker в файл OPFS, чтобы не держать 195 МБ результата целиком. Если это окажется слишком медленным, запасной вариант — JPEG или разрешение в пределах лимита canvas.
- Проверка: эталонный тест «тайлы = целый кадр» на 12 МП в Node и Chromium, на стыках не должно быть ни одного пикселя с другим уровнем.

Нехватка памяти:
- До начала работы оцениваем память как сумму w×h×4 по всем буферам. Если оценка больше бюджета (старт 512 МБ, уточняется по этапу 0, настраивается), сразу спускаемся по лестнице деградации, а не ждём падения.
- Лестница: 1) тайлы меньше, 2048 → 1024; 2) экспорт в уменьшенном разрешении, длинная сторона 6000, затем 4096; 3) экспорт в размере рабочей копии. Пользователь видит, какое разрешение получилось и почему.
- Ошибки выделения памяти (`RangeError`, `null` вместо контекста canvas, событие `webglcontextlost`) перехватываем и переходим на следующую ступень.
- Выгрузку вкладки (jetsam) перехватить нельзя. Поэтому проект и прогресс экспорта сохраняем в IndexedDB/OPFS до тяжёлого шага. После перезагрузки приложение видит незавершённый экспорт и предлагает повторить его в меньшем разрешении.
- Стресс-тест до принудительной выгрузки вкладки не проводим без отдельного подтверждения владельца. На этапе 0 память оцениваем безопасными шагами: сначала 12 МП, затем 48 МП с одним буфером, с остановкой при первом признаке проблемы.

## 5. Инструменты для татуировщика

Все пороги ниже — стартовые значения. Каждый настраивается пользователем и хранится в настройках, ни один не зашит в код. Калибруем их на реальных работах студии вместе с Владимиром.

Проверки выдают предупреждения о возможной потере читаемости, а не прогноз того, как тату будет выглядеть после заживления: заживление зависит от кожи, техники, пигмента и ухода, и приложение этого не знает.

### 5.1 Анализ контраста
- Карта соседних областей после упрощения до 3–5 уровней: для каждой пары соседей ΔL* и ΔE2000.
- Пары с ΔL* ниже порога (старт: 15) подсвечиваются с предупреждением «граница может потерять читаемость со временем».
- Отдельная проверка «цвет на цвете»: две заливки с похожей светлотой, но разным оттенком читаются хуже, чем выглядят на экране. Показываем ч/б-превью рядом.
- В прототипе уже считается `boundaryContrast` (TECHNICAL_RESEARCH, 5.6).

### 5.2 Упрощение цветовых масс под пигменты
- Палитра студии: набор реальных пигментов (название + sRGB-образец, снятый с выкраса на коже или на бумаге).
- Simplify с ограничением: k-means, центры которого прижаты к пигментам студии, и лимит числа цветов (например, 4).
- Отчёт: какие цвета эскиза не попадают ни в один пигмент ближе ΔE 10, и чем их заменить.
- Black & Grey: перевод в 3–5 разбавлений (тонов серого), значения тонов задаёт мастер.

### 5.3 Подготовка контуров
- Contours и Sketch с выходом в векторный SVG.
- Контроль толщины линии в миллиметрах при заданном физическом размере (DPI считается из ширины в см).
- Проверка минимальной толщины: линии тоньше порога (старт: 0,5 мм) и зазоры между линиями меньше порога (старт: 1 мм) подсвечиваются. Считается через distance transform по маске линий.
- Экспорт трафарета: PDF 1:1 под термопринтер или обычную печать, зеркальный вариант.

### 5.4 Проверка читаемости композиции
- «Взгляд с расстояния»: размытие, соответствующее остроте зрения 1′ при размере эскиза X см и расстоянии Y м. Показываем картинку и метрику IoU Notan (на синтетическом флэше 4 см с 2 м дало 0,53).
- Notan-тест «фигура/фон»: доля тёмного, число крупных тёмных пятен, есть ли доминирующая масса.
- Превью «возможное расплывание»: растекание линии (дилатация тёмного, старт 0,1–0,3 мм) + снижение контраста + лёгкое размытие, все параметры настраиваются. Это визуальная эвристика, не медицинская модель и не прогноз заживления. Подпись в интерфейсе: «так может снизиться читаемость; реальный результат зависит от кожи и техники».
- Превью на коже: наложение эскиза в режиме multiply на 6 тонов кожи (шкала Фицпатрика I–VI) с имитацией того, что белый пигмент на тёмной коже почти не виден.

## 6. Этапы

| Этап | Что входит | Критерии приёмки |

## 7. Риски

| Риск | Что делаем |
| --- | --- |
| Safari выгружает вкладку на 48 МП | на этапе 0 безопасно оцениваем память; декодируем сразу с уменьшением, полное разрешение только тайлами при экспорте, лестница деградации из раздела «Фото 48 МП» |
| Разница WebGL2-шейдеров и CPU-эталона | эталонные тесты с допуском, одинаковые формулы Lab в GLSL и TS |
| Данные PWA удаляются через 7 дней без входа | `storage.persist()`, напоминание «добавь на домашний экран», экспорт проекта в файл |
| Пороги тату-метрик не совпадают с практикой | калибровка на работах студии на этапе 4 |
| Сходство с оригиналом по UI | свой дизайн и названия, сходство только на уровне общих художественных понятий (Notan, Values) |

## 8. Решения до начала разработки

| # | Вопрос | Рекомендация | Почему |
| --- | --- | --- | --- |
| 8.1 | UI-фреймворк | Svelte 5, запасной вариант Preact | маленький рантайм, слайдеры без лишних перерисовок |
| 8.2 | Шкала яркости для Values и Notan | L* по умолчанию, luma как режим совместимости | оригинал считает по luma (Rec.601); L* ближе к восприятию тона, но даст другие границы, чем привык пользователь Color Study |
